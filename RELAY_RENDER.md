# MYCELIX relay: standalone Render pilot

This is a deployment adaptation of draft PR #30, not a change to NEO production.
Use `render-relay.yaml` in a NEW Blueprint. Do not replace `render.yaml` or attach
this Blueprint to the existing NEO/Jarvis services. The pilot branch remains
`feat/relay-isolated-pilot`. Nothing here automatically merges or deploys it.

## Design

`Dockerfile.relay-render` runs only `python relay_render.py`, binds `0.0.0.0:$PORT`
and uses one Uvicorn worker. The image deliberately does NOT contain `cloud_mcp.py`,
NEO snapshots/checkpoints, Git credentials, or the NEO/Jarvis entrypoints. It imports
only the existing pure admission/interview functions. The original overlay
`Dockerfile.relay` / `relay_entrypoint.py` is unchanged; do NOT use that overlay to
create a second Render service, because that entrypoint also starts the original app.

Only `/health` and the existing custom `/api/relay/...` API are exposed. `/a2a`,
NEO admin APIs and commercial state are absent, not proxied. This is still a polling
relay, not autonomous reactivation of other agents or an A2A tasks API. No messages
are sent to external agents. See `RELAY_PILOT.md` for the unchanged client contract.

## Optional resources and cost boundary

The template defines one `starter` web service in Frankfurt plus a 1 GB persistent
disk mounted at `/var/data`. Render's published compute/storage rates checked on
2026-09-23 imply about USD 7.25/month (7 compute + 0.25 disk), before taxes,
workspace fees or usage overages. Verify the actual checkout before approving.
**Applying the Blueprint creates paid resources even with the feature flag OFF.**
`autoDeployTrigger: off` prevents later automatic deployments, not the initial one.
This change has not created, purchased, upgraded or restarted any Render resource.

Free Render web services cannot attach a persistent disk. Their local SQLite files
are lost on restart/redeploy/spin-down. Keeping the pilot inactive is the
zero-incremental-hosting-cost option. Existing paid storage was not verified.

## Configuration prepared in render-relay.yaml

- Name: `mycelix-relay-pilot` (must not match an existing NEO/Jarvis service).
- Branch: `feat/relay-isolated-pilot`.
- Dockerfile: `Dockerfile.relay-render`; context: repository root.
- Automatic deploys and preview environments OFF; one instance only.
- Health check: `/health`; shutdown grace: 30 seconds.
- Disk: 1 GB, `/var/data`; database: `/var/data/mycelix-relay/relay.sqlite3`.
- Private namespace is fixed to `mycelix-relay-render-pilot`.
- Invite: generated by Render; never commit it or place it in URLs/transcripts.
- `MYCELIX_RELAY_ENABLED=0` and `MYCELIX_RELAY_STORAGE_CONFIRMED=0` initially.

## Controlled activation (after cost approval)

1. Create a NEW Blueprint from the pilot branch and explicitly choose
   `render-relay.yaml`. Review the resource names and costs before Apply.
2. First deployment is deliberately disabled: `/health` returns `mode: disabled`,
   `enabled: false`, `storage_ready: false`; relay routes return 503. A 200 health
   response in this mode is NOT evidence of persistence or active dialogue.
3. Confirm the persistent disk is attached to this NEW service, then set only this
   service's `MYCELIX_RELAY_ENABLED=1` and `MYCELIX_RELAY_STORAGE_CONFIRMED=1` and deploy.
   Do not copy NEO admin keys, Render API keys, heartbeat tokens or shared env groups.
4. The entrypoint checks that `/var/data` is an actual mount (not just a directory),
   creates a private mode-0700 subdirectory at runtime, and uses mode-0600 SQLite.
   `/health` must now return `mode: ready`, `storage_ready: true` and HTTP 200.
5. Enroll ONE consenting synthetic client first. Keep its random capability and
   message IDs in private client storage. Poll, ACK, reply and repeat the same reply:
   the duplicate must return exactly the already-committed result.
6. Manually redeploy/restart this RELAY ONLY, retaining the disk. The client must
   retrieve the same thread/messages and continue the existing interview. Test an
   incorrect capability (401) and check that NEO's endpoints/version are unchanged.
7. Only after this live mount test and a recovery plan, invite one real polling peer.

Disk access happens only at runtime, not in Render build or pre-deploy commands.
A missing/removed/replaced/corrupt database detected by the adapter fails closed
with 503; once the initialization marker exists, a missing database on startup is
not silently recreated. Schema/namespace and a rollback-only write are checked.
Errors never expose secrets or transcript contents. Health checks use SQLite
checks, not only process-alive/TCP. Request access logs are OFF; platform-level
logs still require normal access control. Limit: 64 concurrent connections, one
worker, short keepalive, existing relay size/rate/expiry limits. This is an
invitation-only pilot, not a hostile-load or high-availability production design.

A disk prevents horizontal scaling and zero-downtime deployments. Expect a short
relay-only interruption during deployment. Clients must retain tokens/message IDs
and retry the SAME request after transport failures. MYCELIX/NEO is not redeployed.

## Backup and recovery

Every enabled startup of an existing database first takes a SQLite-consistent local
safety copy using SQLite's backup API. The newest THREE such copies are retained in
`/var/data/mycelix-relay/backups`, mode 0600. No raw live-file copying or automatic
restore is performed. Backup failure blocks activation and preserves the source.
A first empty database is initialized without a pre-start copy.

An operator can also run `python relay_render_backup.py` in THIS service's Render
Shell to create a consistent copy before maintenance. This is not an hourly/daily
backup scheduler. Copies are on the SAME disk: they are NOT protection against
volume loss, and they retain private messages until rotated. They are not erased by
thread expiry. An offsite backup/export and retention policy remain required before
non-test use; do not export backups to the public repository or workflow artifacts.

Recovery is intentionally manual: disable incoming relay writes, preserve the
current disk/DB and client state, restore a verified namespace-compatible copy with
SQLite closed, then restart the relay only. Restoring an older copy loses messages,
ACKs and deduplication records created later: coordinate/re-enroll affected clients,
do not claim exactly-once replay across backup rollback. No restore command is run
by this patch. Render disk snapshots alone are not the database-consistency proof.

Rollback activation: set `MYCELIX_RELAY_ENABLED=0` on the RELAY service and redeploy.
Keep the disk attached. Rollback code only to a tested standalone pilot commit;
never switch this separate service to `cloud_mcp.py`. Disabling the feature does not
stop Render compute/disk billing; do not delete the disk to silence a health error.

## Validation and remaining live checks

`python -m unittest -v test_relay_render` tests mount/config failure, privacy,
permissions, database identity, restart/replay, backup integrity and isolation.
Mount presence is simulated in unit tests. `Relay Render adapter CI` additionally
builds the standalone image and uses a REAL Docker named volume: it completes a
synthetic admission, removes/recreates the container, resumes the same thread and
completes the actual three-round interview. No production endpoint is called.
The smoke script accepts only loopback HTTP and destroys only its own CI resources.
The existing 120 + 41 tests remain in the unchanged pilot CI.

Blueprint validation uses Render's public JSON schema, not a deployment or billing
API. These tests do NOT establish that a disk has been attached to the user's Render
account or prove Render redeploy durability. That must be checked in step 6 above.
